# 工作流证据与执行身份契约优化记录（2026-08-20）

## 问题现象

- `accepted-inferred` 过去只检查 source 数量，同一文件重复引用或同源派生图可能被误算成两条独立证据。
- 已接受门窗在宿主墙变化后可能继续保留旧状态，接受结论没有绑定当前几何、拓扑与证据集合。
- 编排器只比较 actor 字符串，同一执行 run 改名后存在自审空间；reviewer 的只读边界也没有进入机器契约。
- 旧 pipeline 状态中的 actor-only `RESOLVED` issue 可能在合同升级后继续被误用。

## 修改内容

1. evidence attach 自动绑定文件内容 SHA-256、根内容集合、lineageId 与 producer；调用者不能覆盖计算出的 lineage。
2. inferred 接受要求至少两份内容不同且根集合不相交的已验证文件；同 bytes 异路径、同根派生图或部分共享上游根均不算独立。
3. 接受结论写入 `claimSnapshot`、`claimHash` 与 `acceptedSourceDigest`。节点、宿主墙、寄生洞口、拓扑或坐标声明变化后，受影响结论失效为 candidate；同步 Viewer 也会比较 snapshot，不能只信状态字符串。
4. execution identity 绑定 actorId、不可变 runId、role、模型、checked-in tool policy digest 与 attestation。P0/P1 必须由 regional/adversarial 只读 reviewer 处理。
5. reviewer policy 无 authority/evidence/pipeline stage mutation 权限；MCP 只暴露当前身份允许的工具，CLI 与 pipeline 同样校验策略。
6. deterministic checker 仅接受固定 provider、固定只读策略和 code/config/input digest；仍必须使用独立 run，并绑定当前输入。
7. V1/旧 V2 状态迁移会重开 legacy issues，并标记 `LEGACY_REVIEW_IDENTITY_RECHECK_REQUIRED`，不继承旧的 RESOLVED。
8. 浏览器编译器不再把只有 `accepted-*` 字符串、但缺 claim/reviewer receipt 的旧条目当成正式结构。
9. Pipeline 每次读取前置 PASS 都会重新哈希其 artifact bytes；typed artifact 必须绑定直接前置 artifact 的真实 SHA，文件替换或漏绑会阻断下游阶段。
